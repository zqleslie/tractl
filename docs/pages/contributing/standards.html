Code Standards
What the linter enforces, why each rule exists, and Go idioms expected in this codebase.

The Gate: make check

Every commit must pass make check. It runs: go vet → gofmt -l → golangci-lint run → go test ./.... The pre-commit hook installed by make setup runs the same targets so you catch failures locally before pushing.

GOWORK=off — The pre-commit hook and CI both run with GOWORK=off so an incomplete root go.sum cannot be masked by the workspace. If your code passes locally with go.work but fails CI, this is why.

Go Rules

RuleWhy
All exported symbols have godoc commentsRequired by golint. Keeps the API self-documented without relying on external docs.
No global mutable stateGlobal vars make concurrency unsafe and tests non-deterministic. Use dependency injection via structs.
No panic() in library codeThe engine must never crash a caller's process. All errors must be returned explicitly.
Errors must be explicit — no silent discarderrcheck linter enforces this. Discarded errors are a leading source of bugs in Go.
Table-driven tests for all validatorsValidators have many edge cases. Table-driven tests make coverage obvious and new cases easy to add.
No cross-imports between internal/ packages at the same levelPrevents circular dependencies. Each package has a defined position in the pipeline.
Terminology must match docs/spec/00_terminology.mdVocabulary drift is a real maintenance problem. "provider" and "adapter" are not synonyms here.

Comments Policy

The codebase has a minimal comments policy — write a comment only when the why is non-obvious. Do not describe what the code does (the code does that). Do not reference ticket numbers or PR descriptions. A good comment documents a hidden constraint, a subtle invariant, or a workaround for a specific upstream bug.

// Bad: describes what, not why
// Increment the counter
counter++

// Good: explains a non-obvious constraint
// GOWORK=off prevents a partial go.sum from masking CI failures
os.Setenv("GOWORK", "off")
