Git Workflow
Branch strategy, commit conventions, and PR process.

Branch Strategy

traCtl uses a simple trunk-based model. All development branches off main and merges back via PR.

Branch patternUse forExample
feat/<desc>New featurefeat/retry-jitter
fix/<desc>Bug fixfix/cycle-detection
test/<desc>Tests only, no behaviour changetest/overlay-conformance
refactor/<desc>No behaviour changerefactor/normalize-pipeline
docs/<desc>Documentation onlydocs/platform-adapter-guide
chore/<desc>Build, tooling, configchore/bump-goja

Commit Conventions

Follows Conventional Commits. The prefix determines how the change appears in the changelog.

feat:     add retry backoff jitter to executor
fix:      resolve cycle detection false positive in planner
test:     add table-driven tests for YAML boolean edge cases
refactor: extract variable resolution into its own package
docs:     add platform adapter deep-dive page
chore:    bump goja to v0.0.0-20260311135729

Scope is optional but helpful for large changes: feat(executor): add connection pool reuse

PR Process

1

Open an issue first

For any non-trivial change, open an issue and get alignment before writing code. This prevents wasted effort on PRs that contradict the architecture.

2

Branch from main

git checkout -b feat/your-feature main

3

Run make check before pushing

The pre-commit hook does this automatically. If you skipped make setup, run it manually.

4

Open the PR with the template

Reference the roadmap phase and milestone. Fill in the architecture notes section — maintainers use it to understand non-obvious decisions.

5

Address review feedback

PRs that contradict a frozen ADR will be closed with an explanation, not silently rejected. If you disagree with an ADR, open an arch-conflict issue — don't work around it.
