Schema & DTOs
Where the schema is defined, what DTOs exist on each surface, and how data moves between them.

Core rule (ADR-001): Every input — regardless of surface — is eventually normalised into a single canonical Go struct: *spec.TraCtlSpec. That struct is the only thing the engine ever executes. DTOs are surface-level conveniences; the spec is the source of truth.

ADR-017 (accepted 2026-06-02): RequestDef is the public API contract for single-request execution — not just a frontend DTO. A Protocol string field is required before the first release. The frontend must own its TypeScript mapper and not route through the Go mapper. See ADR-017 for the full decision.

1. Where the Schema is Defined

The schema has two authoritative sources that must stay in sync:

📄 Go structs — internal/spec/spec.go

The canonical in-memory representation. Every field has both json: and yaml: struct tags that define the exact wire format key names. This is the only place that controls what field names the YAML/JSON files accept.

internal/spec/spec.go — ~350 lines, fully godoc'd

📋 Spec document — docs/spec/tractl_spec.md

The human-readable specification. Section numbers referenced in every godoc comment (e.g. §7.1). If code and spec disagree, the spec wins — open an arch-conflict issue.

docs/spec/tractl_spec.md — normative, version-controlled

2. The DTO Layer — internal/localapi/types.go

RequestDef is the DTO the frontend sends when a user builds a request in the UI. It is a UI-friendly representation — flat, editor-oriented — not the canonical spec format. The mapper converts it to a valid TraCtlSpec before running.

RequestDef ≠ TraCtlSpec. RequestDef is optimised for what the Request Editor screen needs to display and edit. TraCtlSpec is optimised for execution. The mapper (request_mapper.go) translates between them.

Lives in internal/localapi/types.go. This is the public API contract for single-request execution — used by IDE plugins, external tools, and the frontend. ADR-017

type RequestDef struct {
    Protocol   string          `json:"protocol,omitempty"` // ADR-017: default "http"
    ID         string          `json:"id"`
    Name       string          `json:"name"`
    Method     string          `json:"method"`         // "GET", "POST", etc.
    URL        string          `json:"url"`
    Params     []KVRow         `json:"params"`         // query params as rows
    Headers    []KVRow         `json:"headers"`        // key/value pairs with enabled flag
    Body       *BodyDef        `json:"body"`
    Auth       *AuthDef        `json:"auth"`
    PreScript  string          `json:"preScript"`      // JS run before request
    PostScript string          `json:"postScript"`     // JS run after request
    Assertions []AssertionDef  `json:"assertions"`
    Extracts   []ExtractDef    `json:"extracts"`
    Settings   RequestSettings `json:"settings"`       // timeout, failurePolicy, retry
    Env        map[string]string `json:"env"`           // variable overrides
}

type KVRow struct {
    Enabled bool   `json:"enabled"`   // toggled off rows are NOT sent
    Key     string `json:"key"`
    Value   string `json:"value"`
}

Lives in internal/spec/spec.go. Produced by the parser from YAML/JSON files, or built by the mapper from a RequestDef.

type TraCtlSpec struct {
    SchemaVersion        int               // always 1
    Capabilities         []string           // ["protocol.http"]
    Variables            map[string]string
    Workflows            []Workflow
}

type Workflow struct {
    ID            string
    Steps         []Step
    FailurePolicy FailurePolicy   // "resilient" | "failFast"
    Concurrency   int
    Hooks         *WorkflowHooks
}

type Step struct {
    ID         string
    Kind       string             // "request" | "script" | ...
    DependsOn  []string
    Request    *RequestDescriptor
    Assertions []Assertion
    Extracts   []Extract
    Retry      *RetryPolicy
    Timeout    string             // ISO 8601, e.g. "PT30S"
    Hooks      *StepHooks
}

3. The Mapper — Two Separate Paths (ADR-017)

ADR-017 §3: Two mapper paths serve two distinct caller populations. The Go mapper serves external HTTP callers. The TypeScript mapper serves the React frontend. They must produce equivalent output but are owned and maintained independently.

Go mapper — for external callers

internal/localapi/request_mapper.go — converts RequestDef JSON to a single-step YAML spec document. Serves IDE plugins, curl, CI scripts calling POST /api/v1/run.

TypeScript mapper — for the frontend

frontend/src/platform/mappers/requestDefToDocument.ts — converts RequestDef to spec-shaped JSON, sends as WorkflowRunRequest. Frontend must NOT route through the Go mapper.

requestDefToDocument() in internal/localapi/request_mapper.go converts a RequestDef into a map[string]any that the YAML marshaller turns into a full TraCtlSpec. It handles all the impedance mismatches shown above.

// Simplified flow inside requestDefToDocument()

// 1. Merge params into URL
target := req.URL + buildQueryString(req.Params)

// 2. Filter disabled header rows
headers := enabledKVMap(req.Headers)  // map[string]string, only enabled=true rows

// 3. Convert timeoutMs → ISO 8601
timeout := fmt.Sprintf("PT%dS", req.Settings.TimeoutMs/1000)

// 4. Wrap pre/post scripts into step hooks
hooks := map[string]any{
    "beforeStep": Script{Language: "js", Source: req.PreScript},
    "afterStep":  Script{Language: "js", Source: req.PostScript},
}

// 5. Wrap into a one-step TraCtlSpec document
return map[string]any{
    "schemaVersion": 1,
    "capabilities":  []string{"protocol.http"},
    "workflows": []map[string]any{{
        "id": "run", "steps": []map[string]any{step},
    }},
}

4. DTO Flow on Each Surface

No DTO. The CLI reads the raw YAML/JSON file bytes and passes them directly to the parser. The spec structs are populated by yaml.Unmarshal using the struct tags.

// cmd/tractl/run_command.go
bytes, _ := os.ReadFile(cfg.WorkflowFile)
// bytes → parser.Parse() → *spec.TraCtlSpec → engine.Run()

No mapping step. File bytes → *spec.TraCtlSpec directly via the parser.

The frontend sends a JSON-serialised RequestDef as a string to window.tractl.runRequest(). The WASM handler deserialises it, calls requestDefToDocument() to convert it to a spec document string, then feeds that into the engine.

// Frontend (TypeScript)
const json = JSON.stringify(requestDef)  // RequestDef → JSON string
const result = await window.tractl.runRequest(json)

// WASM handler (Go, cmd/wasm/handlers.go)
var req localapi.RequestDef
json.Unmarshal([]byte(args[0].String()), &req)
doc, _ := localapi.RequestDefToYAML(req)   // → YAML spec document
result := engine.RunDocument(doc, "yaml") // → engine executes it
return json.Marshal(localapi.MapRunResult(&result))

Transport: JSON string over syscall/js — no HTTP.

Identical logic to WASM but transported over Wails IPC. Wails automatically serialises Go method arguments and return values as JSON.

// Frontend (TypeScript)
const result = await window.wails.RunRequest(JSON.stringify(requestDef))

// Go (cmd/desktop/app.go)
func (a *App) RunRequest(reqJSON string) string {
    var req localapi.RequestDef
    json.Unmarshal([]byte(reqJSON), &req)
    doc, _ := localapi.RequestDefToYAML(req)
    result := a.eng.RunDocument(doc, "yaml")
    b, _ := json.Marshal(localapi.MapRunResult(&result))
    return string(b)
}

Transport: Wails IPC (JSON over WebView bridge) — no HTTP.

The frontend POSTs a JSON body containing a RequestDef. The handler in handler_run.go deserialises it and follows the same mapper path.

// Frontend (TypeScript)
fetch('http://localhost:7428/api/v1/run', {
  method: 'POST',
  body: JSON.stringify(requestDef)   // RequestDef as JSON body
})

// Go (internal/localapi/handler_run.go)
var req RequestDef
json.NewDecoder(r.Body).Decode(&req)
doc, _ := RequestDefToYAML(req)          // RequestDef → YAML spec doc
result := eng.RunDocument(doc, "yaml")  // engine executes it
jsonResponse(w, 200, MapRunResult(&result))

Transport: HTTP POST JSON body to :7428.

6. TypeScript Types (Frontend)

The frontend has its own TypeScript equivalents of the Go types. These must be kept in sync manually when the Go types change.

TypeScript fileMirrors Go typeUsed by
types/requestDef.tslocalapi.RequestDef + all sub-typesRequest Editor screen, all platform adapters
types/workflow.tsWorkflowRunSummary, StepResultExecution store, Run History screen
components/request-editor/tractlSpecDocumentspec.Assertion, spec.ExtractAssertion and extract panels in the editor

No code generation. TypeScript types are hand-maintained mirrors of the Go types. If you add a field to localapi.RequestDef in Go, you must also add it to types/requestDef.ts — there is no automatic sync.
