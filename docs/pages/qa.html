Developer Q&A
Real questions from real onboarding. Precise answers with file references.

Questions are grouped by topic. Each answer links to the relevant source file or doc page. If your question isn't here, open a GitHub Discussion — not an issue.

Schema & DTOs

Why are there two separate structs — RequestDef and TraCtlSpec? Why not one? ▼

They serve different purposes at different layers.

RequestDef (internal/localapi/types.go) is the UI/API surface model — flat, HTTP-centric, designed for what a form or IDE plugin sends. It has an enabled flag on header rows, timeout in milliseconds, flat PreScript/PostScript strings.

TraCtlSpec (internal/spec/spec.go) is the execution model — nested, protocol-neutral, designed for what the engine runs. Headers are a filtered map[string]string, timeout is ISO 8601, scripts are nested inside StepHooks.

If they were one struct, the engine would need to know about disabled rows and millisecond timeouts. The mapper (request_mapper.go) is the explicit translation boundary between them. See Schema & DTOs for the full breakdown.

Why does KVRow have an enabled field? The spec doesn't have one. ▼

UI ergonomics. The Request Editor lets users toggle a header or param row off without deleting it — useful when debugging ("disable this header and re-run"). The enabled: false row is preserved in the store so it can be toggled back on.

The mapper in request_mapper.go calls enabledKVMap() which filters out any row where enabled == false before building the RequestDescriptor.Headers map[string]string. The engine never sees disabled rows.

Why is the mapper in Go and not TypeScript? ▼

The Local API (:7428) is a public HTTP surface consumed by external tools — IDE plugins, curl scripts, CI tools — that are not TypeScript. Those callers send a RequestDef JSON and need the Go mapper to convert it to a spec document.

However, the React frontend should not go through the Go mapper. It already has TypeScript types and can map to a spec-shaped JSON object itself, then send it as a WorkflowRunRequest. This eliminates the manual sync between localapi.RequestDef (Go) and types/requestDef.ts (TypeScript).

Correct split: Go mapper serves external HTTP callers. TypeScript mapper serves the frontend. They own their own conversion logic.

What is WorkflowRunRequest.Document? Is it a file path? ▼

No — it is the raw content of the YAML/JSON file as a string. Not a path.

There are two separate run endpoints for this reason:

  • POST /api/v1/run — accepts a file path; Go reads the file from disk. Only usable when Go has filesystem access (Local API, Desktop, CLI).
  • POST /api/v1/workflows/run — accepts the document content as a string. Works on all surfaces including WASM (where Go has no filesystem access).

The word "document" in traCtl always means the spec content, not a file container. Same terminology used in ADR-001.

Will RequestDef need to change when GraphQL or gRPC is added? ▼

Decided — ADR-017 (2026-06-02). A Protocol string field is added to RequestDef before the first release. Default is "http" when empty — fully backward-compatible.

Protocol classification per ADR-017:

  • REST — no change. protocol: "http".
  • OData — no change. It is REST with $filter/$select query params.
  • GraphQL — encoding: "graphql" added to BodyDef pre-release. Structured body {query, variables, operationName}.
  • JSON-RPC — no change. Use encoding: "json" with envelope as content.
  • SOAP — deferred to v1.1. Requires encoding: "xml" + XPath extractor.
  • MCP — extensionCall step kind (Phase 4+). Not a RequestDef concern.

Adding Protocol after v1 would be a breaking API change for every IDE plugin and external tool. Adding it now with a default of "http" future-proofs the contract permanently.

Why does RequestDescriptor use Operation instead of Method? ▼

Protocol neutrality. "Method" is an HTTP concept (GET, POST, DELETE). Other protocols use different terminology:

  • HTTP → operation: GET
  • gRPC → operation: /UserService/GetUser
  • GraphQL → operation: query or mutation
  • WebSocket → operation: connect

Operation is the protocol-neutral field that carries whatever the protocol calls its action. The spec comment reads: "the optional protocol-level operation name". Using Method would hard-code HTTP semantics into what is meant to be a universal execution model.

There is no code generation between Go types and TypeScript types. What is the risk? ▼

Manual sync risk. If you add a field to localapi.RequestDef in Go and forget to add it to frontend/src/types/requestDef.ts, the frontend silently ignores it (TypeScript gets undefined) and Go gets the zero value (empty string, 0, nil). No compile error, no runtime panic — just wrong behaviour that only shows up in testing.

Mitigation today: The PR checklist in CONTRIBUTING.md requires updating TypeScript types when Go types change. There is no automated check.

Long-term fix: Generate TypeScript types from Go structs using a tool like tygo or a custom generator. This is not yet implemented — worth tracking as a future improvement.

Engine & Pipeline

When does the UI use RequestDef vs WorkflowRunRequest? ▼

Two completely separate execution paths:

  • Request Editor screen — user builds one request in the UI form. Frontend constructs a RequestDef from form state. Calls tractl.runRequest() or POST /api/v1/run. The Go mapper wraps it into a one-step spec doc.
  • WorkflowCanvas screen / running a YAML file — frontend has the full document content as a string. Sends WorkflowRunRequest{ document: yamlString }. Calls tractl.run() or POST /api/v1/workflows/run. No mapper involved — parser handles it directly.

RequestDef is never used when running a workflow file. WorkflowRunRequest is never used when running a single UI-built request.

Why can't a step depend on a step in a different workflow? ▼

dependsOn within a step only accepts IDs of other steps in the same workflow. Cross-workflow dependencies are declared at the workflow level — workflow.dependsOn: [other-workflow-id].

This is by design: each workflow has its own ExecutionContext with isolated variable scopes. A step in workflow B cannot read extracted variables from workflow A's steps directly. Workflow-level dependsOn guarantees ordering but not variable sharing — that would require spec-scoped extracts (scope: spec).

Why does the engine never panic? What happens on a parse error? ▼

The engine is designed to be called from any surface — CLI, WASM, Desktop, HTTP server. A panic in a server crashes the process. A panic in a WASM binary crashes the browser tab. So all errors are captured in return values instead.

Error fields in RunResult are mutually exclusive — only one can be non-empty:

  • ParseError — YAML/JSON syntax or format error
  • ValidationError — spec is valid syntax but semantically wrong (cycle, missing field)
  • PlanError — engine can't build an execution plan (unsupported capability)

If any of these is non-empty, Workflows is empty — nothing executed. Exit code 2 on the CLI. The surface decides how to display the error.

What is the difference between failurePolicy: resilient and failFast? ▼

Both mark the failed step as failed. The difference is what happens to other steps:

  • resilient (default) — passively skips steps that depend on the failed step. Independent branches (no edge to the failed step) continue running. The workflow finishes with a mix of passed, failed, and skipped steps.
  • failFast — actively cancels the entire transitive dependency subgraph of the failed step AND all remaining unstarted steps. The workflow stops as fast as possible.

Use resilient when you want maximum diagnostic coverage (see everything that fails). Use failFast when a failed step makes all subsequent results meaningless (e.g. auth step failed — no point testing anything else).

If two steps both extract into the same variable name at workflow scope, which wins? ▼

The step that runs last wins. Extracts are written to ExecutionContext.workflowVars under a mutex — last write wins, no conflict error is raised.

This is a silent overwrite — there is no warning. If two parallel steps both extract into vars.token at workflow scope, the result is non-deterministic depending on which step finishes last.

Best practice: use unique variable names per step, or extract with scope: step and reference via ${steps.stepId.extracts.name} instead of relying on workflow-scope variable names for values that change per step.

Surfaces & Platform Adapter

cmd/server and cmd/localapi both exist. Why aren't they one binary? ▼

They do different things:

  • cmd/server — serves the React SPA as static files. Has no engine logic. When the browser loads the app, it downloads tractl.wasm and the engine runs inside the browser.
  • cmd/localapi — runs the engine server-side on :7428. No frontend. External tools (IDE plugins, scripts) call it via HTTP.

They are separate binaries because they serve different audiences. cmd/server is for hosting the web UI. cmd/localapi is for tooling integration. You might run both at the same time: server hosting the UI, and localapi for the VS Code extension.

Why does the WASM surface call tractl.run() instead of making an HTTP request? ▼

Go compiled to WebAssembly runs as a thread inside the browser tab. It can't make outbound HTTP requests to itself — there is no server to call. Instead, cmd/wasm/bridge.go registers Go functions as JavaScript globals (window.tractl.*) using syscall/js.

When the frontend calls await window.tractl.run(doc, "yaml"), it is calling the Go engine function directly — in the same process, in the same tab, with no network round-trip. This means the engine runs fully offline and no workflow data leaves the user's machine.

How does the platform adapter know which surface it's running on? ▼

frontend/src/platform/index.ts detects the surface at runtime in this order:

  1. If window.wails is defined → Desktop surface (Wails injected it)
  2. If localhost:7428 responds to a status ping → Local API surface
  3. Otherwise → Web WASM surface (default)

All three export the same IPlatform interface. React components never check which surface they're on — they call platform.run() and the correct adapter handles transport.

Contributing & Architecture

I found a bug where the ADR says one thing and the code does another. Which is wrong? ▼

The code is wrong. ADRs are the highest authority in the normative hierarchy (ADR-010). If code contradicts an ADR, the code must change — not the ADR.

Open a GitHub issue labelled arch-conflict. Do not work around the ADR in your PR. Do not silently "fix" the code to match what seems logical — the ADR may have context that isn't obvious from the code alone. Maintainers will review promptly.

Can I import internal/engine in my own Go project? ▼

No. Go enforces the internal/ boundary at compile time — packages inside internal/ can only be imported by code within the same module (github.com/tractl/tractl).

The public SDK surface lives in pkg/. When the capability contract layer (Phase 4+) is complete, external Go projects will import from pkg/capability. For now, external tools should use the Local API HTTP surface (:7428) instead of attempting Go package imports.

Why does the planner and compiler exist as separate stages? Why not combine them? ▼

ADR-003 explicitly requires them to be separate concerns. The planner answers "what should execute and in what order" — it resolves capability contracts, activates environments, analyses dependencies, and determines execution strategy. The compiler answers "how should it execute" — it selects runtimes, pre-compiles regex patterns, and binds payloads.

Separating them means: the planner output (ExecutionPlan) is a declarative description of intent that can be inspected, logged, or passed to different compilers. The compiler output (CompiledPlan) is an opaque executable artifact. You can validate the plan without compiling it. You can compile the same plan differently for different targets. Merging them would collapse this flexibility.

What is TOON? Why a third format when YAML and JSON already exist? ▼

TOON is traCtl's own human-readable authoring format. It is a strict subset of YAML — same parser, same struct tags — but with tighter rules: no YAML 1.1 boolean pitfalls (yes/no/on/off are bare strings in TOON, not booleans), stricter escape sequences, no document separators (---).

The motivation: YAML's implicit type coercion has bitten teams before (a value of yes silently becoming true). TOON keeps YAML's readability while eliminating the ambiguous corners. It is the long-term preferred authoring format — YAML is the default for the alpha because it is more familiar.

All three formats produce equivalent *spec.TraCtlSpec after normalisation. Choosing a format is an authoring preference, not an execution difference.

What is a ULID and why does every spec entity get one? ▼

A ULID (Universally Unique Lexicographically Sortable Identifier) is assigned by the parser to every workflow, step, assertion, and extract. The ULID field in each struct has yaml:"-" (never in the file) and json:"_ulid,omitempty" (visible in API responses).

ULIDs serve two purposes: stable correlation of diagnostics events to spec entities across a run (the same ULID appears in trace events, assertion results, and extract results), and reproducible run identification when a fixed TraceID is provided (deterministic seed for tractl.random() and tractl.now() in scripts).

Authors never write ULIDs — they are system-assigned at parse time and must never be committed to workflow files.
