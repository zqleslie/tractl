Welcome to traCtl

A multi-surface API workflow execution and validation platform — declarative, DAG-aware, and scriptable. Runs as a CLI, desktop app, or browser WASM — all from a single Go codebase.

Go 1.26 WebAssembly React 18 + TypeScript Wails Desktop goja JS Sandbox Zustand goreleaser

📦 What is traCtl?

The 30-second elevator pitch before we dive into code.

traCtl lets developers define API workflows as YAML/JSON files — a series of HTTP steps that can depend on each other, pass data between them, run assertions on responses, and execute custom scripts. It features explicit DAG execution, a sandboxed scripting engine, and a pluggable platform layer.

📄 A Workflow File

Declares steps, their HTTP calls, dependencies between them, assertions to verify, and variables to extract.

🔧 The Engine

Parses the file → validates it → builds a DAG → compiles it → executes steps in parallel topological order.

⚛️ The Frontend

A React/TypeScript SPA that visualises the DAG, lets you build requests visually, and shows execution results.

🖥️ Three Surfaces

Same Go engine, same React UI — delivered as CLI, Wails desktop app, or browser WASM app.

A Minimal Workflow (YAML)

# examples/yaml/01-minimal.yaml
schemaVersion: 1
capabilities:
  - protocol.http

workflows:
  - id: minimal-flow
    steps:
      - id: ping
        kind: request
        request:
          protocol: http
          target: "https://jsonplaceholder.typicode.com/todos/1"
          operation: GET

A Real Workflow — Parallel + Dependencies

variables:
  baseUrl: "https://jsonplaceholder.typicode.com"

workflows:
  - id: parallel-dep-flow
    steps:
      - id: step-1            # Wave 1 — runs immediately
        kind: request
        request:
          target: "${vars.baseUrl}/todos/1"
          operation: GET
        assertions:
          - { id: ok, kind: status, op: equals, expected: 200 }
        extracts:
          - { id: title, source: body, path: title, as: title-from-step-1, scope: workflow }

      - id: step-3            # Wave 2 — waits for step-1
        dependsOn: [step-1]
        request:
          target: "${vars.baseUrl}/todos/3"
          operation: GET

⚡ Execution Pipeline

What happens when you call tractl run workflow.yaml — the 6-stage pipeline.

bytes"] --> P["1 PARSE

scheduler/ + executor/"] E --> R["🎯 RunResult

1

Parse — internal/parser

Detects format from file extension (.yaml, .json, .toon). Delegates to the matching sub-parser. Returns a *spec.TraCtlSpec Go struct.

input: []byte → output: *spec.TraCtlSpec
2

Overlay — internal/overlay

Optionally merges patch files onto the parsed spec (like JSON Patch but semantic). Allows environment-specific overrides without touching the base file.

input: *TraCtlSpec + []OverlayFile → output: *TraCtlSpec (modified)
3

Validate — internal/validation

Schema-level checks: required fields, valid kinds, cycle detection in dependsOn graphs. Fails fast with structured ValidationError list.

input: *TraCtlSpec → output: []ValidationError (or nil)
4

Plan — internal/planner

Topologically sorts steps within each workflow using dependsOn edges. Resolves required capabilities. Produces an ExecutionPlan with explicit wave ordering.

input: *TraCtlSpec → output: *ExecutionPlan
5

Compile — internal/compiler

Selects runtime per step (http, script, etc.). Pre-compiles regex patterns for assertions. Binds payload schemas. Produces a CompiledPlan ready for execution.

input: *ExecutionPlan + *TraCtlSpec → output: *CompiledPlan
6

Execute — internal/scheduler + internal/executor

Runs workflows in parallel (up to WorkflowConcurrency). Within each workflow, runs steps in DAG order. Each step: run hooks → execute HTTP → evaluate assertions → extract variables. All tracked in an ExecutionContext with a mutex for thread safety.

input: *CompiledPlan → output: RunResult {Passed, Workflows[], Diagnostics}

📁 Module Map

Every package in one place — 5 lines max. Color = layer.

internal/spec
Canonical data model. All Go structs that represent a workflow document: TraCtlSpec, Workflow, Step, Assertion, Extract. Everything else in the engine passes these types around. Think of it as the TypeScript interfaces file but for Go.
internal/engine
The orchestrator. Wires Parse → Overlay → Validate → Plan → Compile → Execute. Exposes Engine.Run(cfg) and Engine.RunDocument(). Never panics — all errors land in a RunResult struct. The only entry point callers should use.
internal/parser
Format-agnostic parser registry. Detects format (yaml/json/toon) from file extension, delegates to sub-parsers. Returns *spec.TraCtlSpec. Adding a new format = implementing the Parser interface in a sub-package.
internal/validation
Schema + structural validation. Runs after parse and after overlay. Catches missing required fields, invalid step kinds, circular dependsOn references. Returns a list of ValidationError; does not mutate the spec.
internal/planner
DAG planner. Performs topological sort on workflow steps using dependsOn edges. Detects cycles. Resolves required capabilities. Produces an ExecutionPlan — an ordered list of step waves that can run in parallel.
internal/compiler
Plan compiler. Selects the correct runtime (http, script) for each step. Pre-compiles regex assertion patterns so they aren't recompiled per-request. Binds payload schemas. Outputs a CompiledPlan that is truly ready for execution — no more spec lookups needed.
internal/scheduler
Parallel step runner. Takes a CompiledWorkflow and runs steps according to the DAG order. Steps with no pending dependencies start immediately via goroutines. Uses semaphores to enforce concurrency limits. Collects WorkflowResult.
internal/executor
HTTP request executor. Builds the actual http.Request from a CompiledStep, executes it (with retry + backoff), captures response body/headers/status, and attaches an HTTP trace for precise timing (DNS, TCP, TLS, TTFB). Returns a StepResult.
internal/runtime
Mutable execution state. ExecutionContext holds all variable scopes (spec/workflow/env/step) and step outcomes during a run. Protected by sync.RWMutex. Exposes Freeze() which returns an immutable FrozenContext snapshot for script sandboxing.
internal/assertion
Assertion evaluator. Evaluates compiled assertions against a StepResult: status code, body JSONPath, header values, regex matches. Returns AssertionResult with severity (error vs. warning). Severity "warning" fails display but doesn't block the pipeline.
internal/extract
Value extractor. Pulls values out of HTTP responses (body JSONPath, header, status) and writes them into ExecutionContext at a given scope (step/workflow/spec). Step extracts are the mechanism for chaining requests — e.g., step-1 extracts a token, step-2 uses ${steps.step-1.extracts.token}.
internal/sandbox
JS sandbox via goja. Executes user-supplied JavaScript hooks inside a pure-Go JS engine with zero I/O access (no fetch, no fs, no console). Scripts receive a FrozenContext and return a MutationSet. A goroutine enforces a 5-second hard timeout by interrupting the VM.
internal/overlay
Document patch engine. Applies overlay files to a parsed spec before validation. Supports merge actions: replace, deepMerge, append, appendUnique, remove. Targets are JSON pointer paths or semantic selectors. Designed for environment-specific overrides without forking spec files.
cmd/tractl
CLI entry point. Parses flags (--env, --overlay, --output, --verbose), constructs an engine.Config, calls engine.Run(), formats output as text or JSON, exits with code 0/1/2.
cmd/wasm
WebAssembly bridge. Registers Go functions as JavaScript globals (tractl.run(), tractl.parse(), tractl.validate(), etc.) using syscall/js. The React frontend calls these when running in the browser — no HTTP round-trip needed.
cmd/desktop
Wails desktop shell. Wraps the React frontend in a native OS window via the Wails framework. Exposes Go methods to JavaScript via Wails IPC (not WASM). The UI looks the same as the web version but talks to Go over a different bridge.
cmd/server + internal/localapi
HTTP server surfaces. cmd/server serves the React SPA as static files and exposes /api/v1/status. internal/localapi is a full REST API on :7428 for workspace/file/execution management — used by the localApi platform adapter in the frontend.
internal/diagnostics
Observability / tracing. Collects an ExecutionRecord during a run: timing per workflow, per step, per assertion, wait durations, HTTP waterfall. Emits structured trace output. Deterministic with a fixed TraceID seed for reproducible test runs.
internal/normalize
Spec normalizer. Populates default values after parse (e.g., assigns ULIDs to steps with no explicit ID, sets default failure policies). Runs before validation. Ensures the engine never receives a partially-populated spec.
internal/version
Build metadata. Provides Version, Commit, BuildTime constants. Values are injected at link time by goreleaser (-ldflags "-X ..."). Exposed via tractl version and all API status endpoints.
pkg/capability
Public SDK stub. Placeholder for Phase 4 capability contract types. Not currently used by the engine. Will define the interface for third-party protocol providers (gRPC, WebSocket, etc.).

Extract + Chain Example

# Step 1: GET /auth/token — extracts the JWT
extracts:
  - id: token-extract
    source: body
    path: access_token    # JSONPath into response body
    as: jwt               # stored as variable name "jwt"
    scope: workflow       # visible to all later steps in this workflow

# Step 2: GET /users — uses the JWT (dependsOn: [step-1])

  target: "${vars.baseUrl}/users"
  headers:
    Authorization: "Bearer ${steps.login.extracts.jwt}"

Script Sandbox Flow

sequenceDiagram participant EC as ExecutionContext (live, mutex-guarded) participant SB as Sandbox (goja VM) EC->>EC: Freeze() → deep copy all scope maps EC-->>SB: FrozenContext (immutable snapshot) Note over SB: Script runs in isolation
No I/O, no require, 5s timeout SB->>SB: tractl.setVar("key", "value") SB->>SB: return { mutations: [...] } SB-->>EC: MutationSet EC->>EC: Apply mutations (under mutex) Note over EC: Live context updated safely

Why freeze first? Scripts are user-supplied and run in parallel. If they received a live pointer to ExecutionContext, two scripts running simultaneously could race on the same map. The freeze → mutate → apply pattern makes it safe without blocking execution while scripts run.

🐹 Go Concepts for Node.js Developers

You know JavaScript deeply. Here's what the Go patterns map to — and where they diverge.

🔌

Interfaces (Implicit Satisfaction)

Go

If a struct has all the methods an interface declares, it implements it automatically — no implements keyword.

// Node equivalent: class MyPlanner { plan(spec) { ... } // ← TypeScript structural typing } // Same idea — duck typing
🧵

Goroutines vs Async/Await

Go

Go runs concurrent work in goroutines (cheap OS threads). Scheduler uses go func() to launch step executions in parallel.

// Node equivalent: Promise.all([step1(), step2()]) // Go: go step1(); go step2() // + sync with WaitGroup or channels
🔒

sync.RWMutex

Go

Protects shared maps (stepResults, vars) from concurrent read/write races. RLock = many readers OK. Lock = exclusive write.

// Node equivalent: N/A // Node is single-threaded — no races // Go is truly parallel — mutex is essential
📦

embed.FS

Go

The compiled binary includes the entire dist/ folder baked in. No external files needed at runtime — it's a single executable.

// Node equivalent: // Like __dirname + require('./dist/index.html') // but baked into the binary, not the filesystem
🔢

context.Context

Go

Passed as the first argument to every async function. Carries cancellation signals and deadlines. When a parent times out, all children cancel automatically.

// Node equivalent: // AbortController + AbortSignal // ctx.Done() === signal.aborted
📢

Channels (Semaphores)

Go

A buffered channel of size N acts as a semaphore — only N goroutines can acquire a slot. Used to cap script concurrency.

// Node equivalent: // p-limit(N) — concurrency limiter // Same concept, different syntax
❌

Error Handling (No Throw)

Go

Go functions return (value, error). You check the error explicitly every time — no try/catch. Unchecked errors fail linting.

// Node equivalent: const [err, result] = await to(promise) // Go forces you to handle EVERY error
🏷️

Struct Tags (JSON/YAML)

Go

Struct fields have backtick annotations that control JSON/YAML serialisation keys and omitempty behaviour.

// Node equivalent: // Like class-transformer decorators: // @Expose({ name: 'schema_version' }) // or Joi schema field naming
💉

Dependency Injection via Interfaces

Go

engine.Config has optional fields like Planner, Compiler, Evaluator. In tests, inject mocks. In production, leave nil (defaults used).

// Node equivalent: // Like inversify or tsyringe DI // or passing jest.fn() mocks in tests
🌊

syscall/js (WASM Bridge)

Go

Go code compiled to WASM can register JavaScript-callable functions using js.Global().Set("tractl", ...). The bridge file does exactly this.

// Node equivalent: // Like N-API native addons // or Rust wasm-bindgen // Registers Go fns as JS globals
🔗

-ldflags (Build Injection)

Go

goreleaser injects Version, Commit, BuildTime into the binary at link time. No config file needed at runtime.

// Node equivalent: // Like Webpack DefinePlugin // process.env.VERSION at build time // Baked into the binary, not the env
🔄

Topological Sort (DAG)

Algorithm

Step ordering: DFS-based topo-sort on dependsOn edges. Steps in the same wave have no edges between them — they run in parallel. Cycle = validation error.

// Node equivalent: // Like npm dependency resolution // or Webpack module graph ordering

Complete Go → Node.js Mental Model

Goroutines vs Worker Threads vs async/await ▼

Node.js has one thread (event loop) + optional Worker Threads for CPU work. Go has goroutines — lightweight cooperatively-scheduled "green threads" that are multiplexed across OS threads (GOMAXPROCS). traCtl uses goroutines to run multiple workflow steps truly in parallel — something that's hard to express cleanly in Node. The sync.WaitGroup is the Go equivalent of Promise.all() — you spin up N goroutines, wait for all to complete, then collect results.

Go maps are NOT safe for concurrent access ▼

In Node.js, you never think about concurrent map access because there's only one thread. In Go, if two goroutines write to the same map[string]string simultaneously, it panics at runtime with a "concurrent map writes" error. That's why ExecutionContext wraps all its maps in a sync.RWMutex. RLock() allows multiple concurrent readers. Lock() blocks until all readers/writers are done, then grants exclusive write access.

Why goja instead of a V8 binding? ▼

V8 is a C++ library. Binding it into a Go program is complex and creates a large cross-compilation dependency (hard to produce a WASM binary with V8 inside another WASM binary). goja is a pure-Go ES5+ JavaScript engine — no C dependencies, cross-compiles to any target Go supports (including WASM), and is fast enough for small scripts. The tradeoff is no ES module support and limited ES2020+ features. For hook scripts that just manipulate variables, this is fine.

What does "no panic" mean in practice? ▼

Go's panic() is like throwing an uncaught error that unwinds the call stack. In production Go servers you typically add a recover() middleware to catch panics. traCtl's engine is designed to never panic in the critical path — every error is captured in a return value (RunResult.ParseError, RunResult.ValidationError, etc.) and propagated up gracefully. The exit code is 0 (all passed), 1 (assertions failed), or 2 (pipeline error — parse/validate/plan failed). This makes it reliable in CI scripts.

🔐 Security & Anti-patterns

Honest assessment of the codebase — what's solid, what needs watching.

What's Well Done

✅

JS Sandbox — No I/O Access

Scripts run in goja with zero filesystem, network, or require access. The only injected APIs are tractl.setVar(), tractl.cancel(), tractl.random(). Cannot exfiltrate data or make HTTP calls.

✅

Credential Header Masking in Traces

Authorization, X-API-Key, and similar headers are redacted in diagnostics output so tokens don't appear in trace logs.

✅

No Panics in Critical Path

All errors are captured in RunResult return values. The CLI never crashes unexpectedly; it exits with a structured error message and code 2.

✅

Thread-Safe ExecutionContext

sync.RWMutex protects all shared maps. Scripts work on immutable FrozenContext copies — no goroutine can corrupt another's state.

✅

Validation Before Execution

The spec is fully validated (including cycle detection) before any HTTP requests are made. Malformed specs fail loudly at Stage 3, not mid-execution.

Things to Watch

⚠️

Credential Masking Incomplete — Response Bodies

Headers are masked in traces, but response body contents are not. If an endpoint returns a token in its response body and a diagnostic captures the body, the token appears in plaintext. Extend masking to body extraction targets marked as sensitive.

⚠️

LocalAPI Has No Authentication

The server on :7428 assumes a trusted local environment. It has permissive CORS (any origin). Any web page open in the user's browser can call it. Fine for a local dev tool; needs auth if ever exposed to a network.

⚠️

No Rate Limiting on LocalAPI

A malicious page (or runaway script) could hammer :7428 with thousands of workflow runs. Add a simple token bucket or request queue before exposing to production traffic.

⚠️

Retry Backoff Has No Jitter

Retry logic uses deterministic exponential backoff. Many clients retrying the same endpoint simultaneously will create synchronized load spikes. Add ±10% random jitter — standard practice (AWS SDK does this).

⚠️

HTTP Client TLS Verification — Verify Default

Confirm that the default HTTP client in executor does not set InsecureSkipVerify. Go's http.DefaultTransport is strict by default, but custom clients sometimes disable it for "dev convenience" and get merged as-is.

🔴

Future: Env Var Storage Must Encrypt at Rest

Phase 4 plans a workspace Store for environment variables (API keys, tokens). These MUST be encrypted at rest (OS keychain or AES-GCM with a derived key). Storing them as plaintext JSON on disk is a common mistake that leads to credential leaks.

🔴

No Audit Trail

There is no log of who ran which workflow when. Acceptable for a single-user CLI. A multi-user server mode (planned) MUST add structured audit logging before going to production.

Anti-patterns Observed

Step Hooks Mutate Context After Execution — User Confusion Risk ▼

The beforeStep and afterStep hooks currently run after the scheduler has already executed the step (architectural limitation in the current scheduler). This means a beforeStep mutation won't actually affect the step it's "before". The code acknowledges this and is pending a scheduler refactor. Risk: developers writing hooks will find their mutations have no effect on the current step and debug for hours. Mitigation: document this clearly in the spec and add a warning log when beforeStep mutations are applied.

Variable Scope Shadowing — Silent Override ▼

A workflow-level variable with the same name as a spec-level variable silently wins. There's no warning when this happens. A developer who unknowingly uses the same variable name in two scopes will get surprising results. Best practice: prefix workflow variables (e.g., wf_myVar) or add a lint rule that warns on scope shadows.

Unresolved Variables Silently Become Empty Strings ▼

If you reference ${vars.typo} and "typo" doesn't exist, the variable resolves to an empty string. The request is sent with an empty URL segment or blank header, and you get a confusing HTTP error instead of "variable not found". A strict mode that fails validation on undefined variable references would catch this early.

🎯 Self-Check Quiz

Test your understanding before your first PR. Answer these — if you're unsure, you know exactly what to ask.

1. You write a step with dependsOn: [step-a, step-b]. What does this guarantee about execution order?
step-a runs before step-b before this step (sequential chain)
step-a AND step-b must both complete before this step starts; step-a and step-b may run in parallel with each other
This step waits for step-a OR step-b (first to finish wins)
Correct. dependsOn is an AND condition — all listed steps must succeed. But step-a and step-b themselves may have no edge between them, so the scheduler runs them in parallel (same "wave"). The DAG only guarantees ordering at the edge boundary.
2. An extract with scope: workflow vs scope: step — what's the difference?
scope: workflow persists the value to disk; scope: step keeps it in memory
scope: workflow makes the extracted value available to all later steps in the same workflow; scope: step only makes it available within the extracting step's own result
There is no functional difference; scope is only for documentation
Correct. Scope controls where in the ExecutionContext the variable is written. workflow scope → workflowVars map → readable by later steps via ${steps.id.extracts.name}. step scope → only on the StepResult itself, not promoted to the shared context. Use workflow scope when a later step needs the value.
3. You're in a JS hook script. You call tractl.setVar("token", "abc"). When does ExecutionContext actually get updated?
Immediately — tractl.setVar is a live reference to the Go context
After the script finishes — mutations are collected in a MutationSet and applied in bulk back to the live context under a mutex lock
Never — scripts can only read context, not write to it
Correct. Scripts operate on a FrozenContext (immutable deep copy). tractl.setVar() accumulates mutations in the MutationSet. Only after the script returns does the sandbox.Execute() caller apply those mutations to the live ExecutionContext under a mutex. This prevents concurrent scripts from racing on the same map.
4. What exit code does the CLI return if the spec file has a YAML syntax error?
Exit 1 — the workflow "failed"
Exit 2 — a pipeline stage (parse) failed before any execution occurred
Exit 0 — traCtl never exits non-zero for errors, only for assertion failures
Correct. Exit code convention: 0 = all assertions passed, 1 = assertions failed (the workflow ran but checks failed), 2 = pipeline error (parse, validate, plan, or compile failed — the workflow never got to execute). This makes it easy to distinguish test failures from infrastructure/config errors in CI.
5. You're building a feature that needs to call the engine from a new surface (e.g., a VS Code extension). What's the minimal thing you need to do?
Rewrite the engine package to accept a new surface-specific Config type
Implement the IPlatform interface in the frontend's platform/ directory (if UI needed), or directly construct an engine.Config and call engine.Run() from Go (if no UI). The engine itself is surface-agnostic.
Fork cmd/server and modify it to accept VS Code requests
Correct. The engine is completely surface-agnostic — it just takes a Config struct. On the Go side, any caller can import internal/engine and call engine.Run(). On the frontend side, add a new platform adapter in platform/ that implements IPlatform. The React components never need to change — they call the IPlatform interface regardless of what's underneath.
6. A step has assertions[].severity: warning. The assertion fails. What happens?
The step is marked failed; dependent steps are blocked
The assertion failure is recorded and visible in output, but the step is NOT marked failed. Dependent steps proceed normally. The run still exits 0 if all error-severity assertions pass.
Warnings are ignored completely and don't appear in output
Correct. severity: warning is a soft check. It appears in the diagnostic output (so you can see it) but does not affect step state or dependent step scheduling. This is useful for "should have" checks that don't break the pipeline — e.g., checking a response header that's expected but not required.
